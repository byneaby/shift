# Разделение филиалов

Пока клуб один, филиал в системе тоже один, и всё описанное ниже незаметно.
Как только у клуба появляется вторая точка, нужно, чтобы кассир первой не видел
и не правил данные второй — иначе выручка и остатки перемешаются.

## Как это работает

Филиал сотрудника лежит **в токене** (claim `branch_id`), а не в запросе: клиент
не может сказать серверу, от чьего имени он работает. Токен выдаётся при входе из
`Employee.BranchId`, см. `AuthService.CreateToken`.

Правила разбора филиала собраны в `src/ShiftClub.Server/Auth/BranchScope.cs`:

| Метод | Где применять | Что делает |
|---|---|---|
| `ResolveFilter(requested)` | выборки (`GET`, список) | подставляет филиал сотрудника, если тот не указан; отказывает, если спросили чужой |
| `ResolveBranchIdAsync(db, requested, ct)` | запись (`POST`, `PUT`) | то же, но обязан вернуть один филиал: сотруднику без привязки берёт единственный, а если филиалов несколько — просит указать явно |
| `EnsureBranchAllowed(branchId)` | операции по id записи | проверяет филиал уже найденной записи (например, кассы при открытии смены) |

Право `branches.manage` снимает ограничение: с ним можно работать с любым
филиалом, указав `branchId` в запросе. Это право есть у роли владельца.

Сотрудник без `BranchId` (владелец сети, настройка после установки) по-прежнему
видит всё — но при записи в сети из нескольких филиалов получит понятную ошибку
вместо молчаливой подстановки «первого по дате создания», как было раньше.

Отказ в доступе возвращается как `403` с `errorCode = "branch_forbidden"` и
пишется в лог предупреждением, а не ошибкой: это не поломка сервера, и в списке
ошибок клуба (`/system`) таким записям не место.

## Что уже закрыто

- Список филиалов (`/api/branches`) — привязанный сотрудник видит только свой.
  Панель берёт «свой» филиал из начала этого списка, поэтому это важнее всего.
- Выборки: зоны, ПК, кассы, тарифы, карта зала, уровни лояльности, доступные ПК
  под бронь, поиск клиентов.
- Запись: тарифы, ручные станции (PS5 и прочее), новости, бар, каталог
  программ, импорт клиентов — филиал берётся из токена, а не «первый по дате».
- Открытие кассовой смены — на кассе чужого филиала запрещено.
- Часовой пояс для брони берётся из филиала сотрудника: в сети в разных поясах
  «сегодня» у филиалов разное.

## Что осталось и почему

**Операции по id существующей записи** (закрыть смену, править тариф, отменить
бронь) проверяют только право, но не филиал записи. Чтобы попасть на такую
запись, её id нужно откуда-то взять, а все списки уже отфильтрованы по филиалу —
то есть угадать id. Полная проверка требует правки каждого метода сервисов, и её
имеет смысл делать вместе с переходом на общий фильтр уровня `DbContext`
(global query filter), а не точечно.

**Публичные ручки** (`/api/public/*`: табло цен, меню бара, информация о клубе,
мини-приложение в Telegram) берут первый филиал: у анонимного запроса филиала
нет. Для сети сюда нужен явный выбор филиала — код филиала в адресе табло и в
ссылке мини-приложения. Это меняет контракт публичных ручек и клиентов табло,
поэтому вынесено отдельно.
